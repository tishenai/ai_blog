你上传了一份 50 页的技术报告。Claude 把整个文件转成文本，然后对全文本做 embedding，再把整段塞进上下文窗口。这个过程消耗多少 token？一份 50 页的 PDF 大约是 2 万到 5 万 token。如果你一天处理 10 份这样的文件，就是 20 万到 50 万 token。一个月下来，这个数字很容易就超过了你上下文窗口总消耗的 60%。

## 上下文窗口为什么会被撑爆

要理解 Token Saver 在做什么，先要理解上下文窗口真正的消耗结构。

当 Claude 处理一份 PDF，它不是像人类那样"阅读"的。人类的阅读是选择性的——你跳过目录，跳过重复的章节标题，跳过表格的边框说明文字。LLM 的处理方式是不同的。在没有特殊指令的情况下，模型倾向于认为输入文本里每一个字符都有潜在的语义权重，都会影响它对整体内容的理解。

这在理论上是对的。在实践里，这意味着模型会把大量没有实际信息量的结构性文本也当作有效输入处理。

把这些无效和低效的 token 加在一起，就是一份 PDF 里"看起来有信息但实际没价值"的部分，合计可能达到 55% 到 70%。

Token Saver 做的事，就是把这个结构识别出来，然后把有用的部分提取出来，把浪费的部分剔除掉。

## 混合 RAG 的工作原理

Token Saver 的核心是一个混合 RAG 架构，这里的"混合"指的是两种检索方式的组合：向量检索和关键词检索。

向量检索是 RAG 系统里最常见的方式。模型先把文档切成小块，给每一块生成一个向量 embedding，存储在向量数据库里。当用户提问时，问题本身也被转成向量，然后在向量数据库里做相似度搜索，找到语义上最接近的文本块。

这种方式的优势是语义理解——你可以用"如何改进 RAG 系统"来检索，模型会找到关于 RAG 优化的内容，即使那个文档里没有出现"改进 RAG"这个原词。

但向量检索有一个问题：它对精确关键词不敏感。"2024 年第三季度的营收增长了 15%"，向量检索可能找到语义相近的段落，但不一定能精确命中"2024 年第三季度"和"15%"这两个关键数字。

关键词检索则相反。它对精确匹配非常有效，但对同义词和语义变化不友好。

Token Saver 的混合策略是：先用向量检索找语义相关的候选块，再用关键词检索做二次验证和精调。两种方式的结果取交集，再结合一个信任度评分，决定最终送进上下文的 token 块是哪些。

这个策略在处理 PDF 时候特别有效，因为 PDF 里的技术术语往往是精确的——一个函数名、一个参数名、一个版本号——这些词向量检索可能无法精确命中，但关键词检索可以。

## 本地运行的限制和代价

Token Saver 是一款开源 MCP 扩展，可以在本地运行，不需要把数据送到第三方 API。这个特性对它来说是双刃剑。

先说优势。本地运行意味着 PDF 内容不需要经过任何第三方服务器。对于处理包含敏感财务数据、医疗记录、内部战略文档的场景，这是一个不可绕过的前提条件。本地运行的延迟也更低——没有网络请求，token 处理完全在本地完成，对于大批量文档处理场景，总耗时可以减少 30% 到 50%。

但本地运行也有代价。向量数据库和 embedding 模型需要在本地部署和运行。Token Saver 推荐的方案是轻量级向量数据库（如 Chroma 或 Qdrant）加上一个小型 embedding 模型（如 sentence-transformers 系列的轻量版本）。即便如此，第一次建立索引的耗时仍然显著——一份 200 页的 PDF，建立向量索引的时间可能在 30 秒到 2 分钟之间。

这引出了一个关键问题：Token Saver 节省 token 的前提，是你愿意为节省 token 付出的计算成本。这个成本不只是硬件——还包括建立和维护向量索引的操作复杂性。对于偶尔处理一两份 PDF 的场景，这个开销可能不值得；对于每天处理几十份 PDF 的场景，这个开销是可以摊薄的。

## 92% 这个数字是怎么算出来的

Token Saver 官方宣传里最抓眼球的是"削减 92% 到 99% 的 token 消耗"。这个数字需要仔细看它的计算口径。

第一层是 PDF 转文本阶段的 token 节省。Claude 的 PDF 解析会对每一页生成文本内容，然后发送给 API。原始 PDF 转文本的 token 消耗和实际有效内容之间存在差距。以一份 30 页的技术报告为例，转文本后的 token 总量可能是 12000，Token Saver 的过滤最终只把 3000 到 4000 token 送进上下文窗口，这一步的削减率大约是 65% 到 75%。

第二层是上下文窗口的复用率节省。这一层是 Token Saver 更核心的创新点。它不是简单地把 PDF 内容切块送进去就结束，而是维护一个本地知识库，对已经处理过的 PDF 内容做持久化存储。当用户再次提问时，如果已有内容可以回答，就不需要重新送入上下文窗口。

这是 RAG 系统的一个核心价值主张：同样的文档内容，在多轮对话里只消耗一次 embedding token，之后每次问答只消耗用户问题的 token 和检索结果的 token。

把这两层节省叠加计算：一份 PDF 的初始处理消耗 65% 的原始 token，之后的每次问答几乎不产生额外的文档 token，Token Saver 官方在多轮对话场景下报出了 92% 到 99% 的综合削减率。

但这里有一个需要注意的边界条件：这个 92% 到 99% 的数字，是在一个假设前提下成立：同一份 PDF 被多次用于多轮问答。如果只是单次问答，token 节省率会显著降低，更接近 65% 到 75%。

## 这件事的深层含义

Token Saver 解决的不是 PDF 处理这一个具体问题，它指向的是 LLM 应用架构里的一个根本矛盾：上下文窗口是昂贵的，但让模型理解文档需要把整个文档送进去。

这个矛盾在模型能力越来越强的背景下会越来越尖锐。

当 GPT-4 或者 Claude 处理一份文档的时候，它们的理解深度取决于对文档结构的把握。但理解得越深，需要的上下文就越多；上下文越多，消耗的 token 就越大；token 消耗越大，成本就越高。这个链条不是线性的——它是阶梯性的，因为上下文窗口有上限，超过上限就必须截断，而截断会造成信息损失。

Token Saver 提供了一个局部最优解：在上下文窗口上限不变的前提下，通过更高效的 token 使用方式，延长模型能够有效处理文档的篇幅和对话轮次。

从更宏观的角度看，这件事和 AI 时代的数据基础设施演进方向是一致的。当模型推理成本持续下降的时候，更大的瓶颈会转移到数据质量、数据组织和数据检索上。Token Saver 是这个方向上一个具体的产品实现——它不是在做模型能力的事情，它在做的是让已有的模型能力被更高效地使用。

这个方向的天花板还很高。如果有一天 embedding 模型的精度足够高、本地向量数据库的性能足够好、混合检索的策略足够智能，理论上可以让任何长文档的 token 消耗降到当前的 10% 以下，同时保持甚至提升模型的回答质量。

那一天，上下文窗口的大小限制对 AI 应用的影响会变得非常小。到那个时候，真正决定 AI 应用深度的，就不是模型能处理多长的文本了，而是我们有没有能力把最有价值的信息以最高效的方式组织起来。

Token Saver 是这条路上的一个小步，但它指向的方向是对的。
